## 1. 개요

### 1.1 한 줄 소개
공공데이터로 서울 여행 동선을 짜고, 그 동선과 같은 국적 여행자의 실제 지출 통계를 바탕으로 **범위와 근거가 있는 여행 경비**를 보여주는 방한 외국인 전용 여행 계획 서비스.

### 1.2 해결하는 문제
외국인 여행자는 한국 물가 감각이 없어 예산을 세우기 어렵다. 동선은 스스로 찾아 짤 수 있지만 "실제로 얼마를 쓰게 될지"는 알 수 없다.

### 1.3 포지셔닝 (기획서 대비 수정)
- 기존 표현 "외국인 대상 한국 여행 계획 서비스가 없다"는 사용하지 않는다. AI 일정 추천은 이미 여러 서비스(크리에이트립, 비짓서울 여행 플래너 등)가 제공한다.
- KOREADY의 차별점은 **확정된 동선을 입력으로 받아, 국적별 실제 지출 통계로 항목별 경비 범위를 계산하고, 그 근거를 화면에 명시한다**는 점이다.
- 1인당 지출 감소 같은 거시 지표는 문제의 직접 근거로 쓰지 않는다. 사용자 인터뷰 결과로 문제를 뒷받침한다.

### 1.4 목표와 KPI

| 지표 | 정의 | 목표(가설) |
|---|---|---|
| 경비 화면 도달률 | 조건 입력을 시작한 세션 중 예상 경비 화면에 도달한 비율 | 50% 이상 |
| 실제 지출 입력률 | 여행 종료된 일정 중 지출 입력을 완료한 비율 | 15% 이상 |
| 예측 오차율 | \|예상 중간값 − 실제 지출\| ÷ 실제 지출 (1인 기준 총액) | 25% 이하 |
| 범위 적중률 | 실제 지출이 예상 범위(알뜰~여유) 안에 든 비율 | 60% 이상 |

목표 수치는 첫 유저 테스트 후 재조정한다.

## 2. 범위

### 2.1 MVP에 포함
Figma 「범례·API 목록」(2026-10-28)의 화면 번호와 서버 API 32개 기준이다.

| ID | 기능 |
|---|---|
| F1 | 조건 입력 (국적, 여행 지역=서울 고정, **숙소 위치**, 날짜, 인원, 1인 희망 예산, 여행 테마 8종) |
| F2 | 장소 선택(추천 순위): 카테고리·숙소 위치·인기도로 순위를 매긴 후보를 동선 전에 보여주고 사용자가 담음 |
| F3 | 동선 설계·편집, 일자별 지도로 보기, 계획 확인 탭 (대중교통 이동시간·운임 계산) |

### 2.2 MVP에서 제외
- 서울 외 지역: 조건 입력 화면은 "현재 서울 여행만 지원해요."로 안내한다.
- 숙박비와 항공권: 9/22 결정. 경비 화면과 희망 예산 모두 "숙박·항공 제외" 기준이다.
- 실시간 결제·예약 연동.
- 장소 추가(동선 화면의 03-09, 05-07, 07-12): Figma에 화면은 있으나 API가 없다. 후순위.
- 장소 상세의 주변 교통(07-11): API 없음.

## 3. 사용자와 이용 흐름

### 3.1 타깃
- 1차: 서울을 처음 또는 두 번째로 방문하는 일본·중국 국적 자유여행자
- 2차: 대만·홍콩, 미주·유럽 여행자
- 특징: 동선은 스스로 찾지만 물가 감각이 없다. 여행 전에는 폰 브라우저나 앱에서 계획하고, 여행 중에는 저장된 일정을 오프라인으로도 본다.

### 3.2 흐름
```
온보딩 → 회원가입 / 로그인(F11) → 메인(홈) → 조건 입력(F1, 숙소 위치 포함) → 장소 선택(F2)
      → 동선 확인·편집(F3, 지도로 보기) → 예상 경비(F4) → 여행 확정 → [여행: 계획 확인·지도·챗봇]
      → 지출 입력(F5) → 리포트(F6)
```
하단 네비게이션은 5탭이다: 홈 · 지도 · 챗봇 · 계획 확인 · 마이페이지. 헤더에는 언어·통화 설정(F7)과 알림(F14)이 있다. 지도·계획 확인 탭은 "지금 여행"(`GET /api/trips`)을 받아 보여준다.

## 4. 기능 명세

### F1. 조건 입력
Figma 「02 조건 입력」「02a 숙소 위치 검색」「02b」(10/16 이후 시안 없음, 이전 시안 사용) 기준이다. 선택지는 `GET /api/meta/options`로 받는다.

| ID | 요구사항 |
|---|---|
| F1-1 | 출발 국가/국적을 선택한다 ("환율 및 맞춤 가이드 반영"). 저장은 **권역 코드**로만 한다 (§11) |
| F1-2 | 여행 지역은 "서울 (Seoul)"로 고정 표시하고 "현재 서울 여행만 지원해요."를 안내한다 (MVP는 서울 한정, §2.2) |
| F1-3 | **숙소 위치**를 입력한다. 두 가지 중 하나를 고른다. ① "숙소를 선택해주세요" → 숙소 검색(02a) 또는 "지도에서 선택"(02b: 주소·장소명 검색 + 지도 핀, 핀 위치의 주소와 서울 여부 확인). ② "아직 숙소를 정하지 못했어요" → 지역을 고르면 그 지역의 중심을 숙소로 보고 "서울에서 가까운 장소부터" 추천한다. 지도 핀 선택은 검색이 실패해도 항상 가능해야 한다 |
| F1-3a | 숙소 좌표가 서울 범위 밖이면 "현재 서울만 지원합니다" 안내를 표시하고 진행을 막는다 |
| F1-3b | 숙소 검색(02a)은 TourAPI 숙박 데이터를 **서버 DB에 적재한 뒤 자체 검색**한다 (`GET /api/lodgings`). 숙박정보 조회(`searchStay2`)로 서울 숙박을 국문·영문으로 적재해 이름·주소로 검색한다. 키워드 검색(`searchKeyword2`)은 v4.3부터 관광타입 필터가 없어 숙박만 골라낼 수 없고, 국문 키워드 검색이라 영어 입력에 약하기 때문이다. 결과 화면에 "숙박 시설 정보 · 한국관광공사"를 표시한다. 개인 숙소(에어비앤비 등)는 검색되지 않을 수 있으므로 지도 핀·지역 선택을 안내한다 |
| F1-3c | 주소·장소명 검색(`GET /api/geo/search`)과 핀 위치 주소 조회(`GET /api/geo/reverse`)의 **제공자는 `[결정 필요: Q10]`** |
| F1-3d | 숙소는 나중에 바꿀 수 있고, 바꾸면 거리 점수와 동선 기점이 다시 계산된다 (선택한 장소는 유지). 장소 선택 화면 상단의 "변경"으로 진입한다 |
| F1-4 | 일정은 "일정 & 동반 인원" 카드에서 날짜 선택 카드(시작~종료)로 정한다. 요약은 "2026. 09. 18 ~ 09. 20 · 2박 3일"이고 "변경"으로 다시 연다. 과거 날짜는 선택할 수 없다 |
| F1-5 | 인원은 − / + 스테퍼로 정한다. 안내 문구는 "만 15세 이상 성인 기준" (조사 대상 연령과 일치). 상한은 `[확인 필요: Figma에 상한 없음, 기존 안은 10명]` |
| F1-6 | 1인 희망 예산: 30만/50만/100만원 칩 + 직접입력. 안내 "숙박과 항공 제외 예산을 작성해주세요" |
| F1-7 | 여행 테마 다중 선택, **8종**: 쇼핑, 체험 관광, 음식, 축제/공연/행사, 역사 관광, 자연관광, 레저 스포츠, 문화 관광. 이름은 신분류체계 대분류 명칭과 맞췄다 (매핑 §5A.2, 경비 연결 §5.4) |

버튼: "이 조건으로 여행 계획 생성하기 →" (Figma 현행). 누르면 `POST /api/trips`로 여행을 만들고 장소 선택 화면으로 이동한다. 예정·진행 중 여행이 이미 있으면 서버가 거절한다 (API 16).

수용 기준: 필수 항목(국적, 숙소 또는 "아직 정하지 못했어요"+지역, 기간, 인원)이 비면 버튼이 비활성화된다. 다음 화면이 장소 선택이므로 버튼 문구는 "추천 장소 보기"가 더 정확하다 (§10).

### F2. 장소 선택 (추천 순위)
Figma 「02c 장소 선택」 기준이다. 조건 입력 직후, 동선을 만들기 전에 보여주는 화면이다. 사용자가 장소를 **담으면** 그 장소들로 동선(F3)을 만든다. 목록은 `GET /api/trips/{tripId}/candidates` (검색어, 페이지당 5곳).

화면 구성: 상단에 숙소 카드(숙소명 + "기준점", 기간·인원·1인 예산, "변경")와 "선택 조건" 칩, 장소 이름 검색창, 카테고리 탭, 일정 일수 안내 카드, 5곳 목록, 숫자 페이지네이션, 하단 선택 바.

| ID | 요구사항 |
|---|---|
| F2-1 | TourAPI 적재 DB에서 테마 → 분류체계 매핑으로 후보를 필터링한다. 숙소 좌표는 후보 필터가 아니라 **거리 점수**로 반영한다 (§5A.2) |
| F2-2 | 후보를 **순위**로 보여준다. 점수는 테마 적합도, 방문자 수 기반 인기도, 숙소와의 거리, 정보 완성도의 가중합이다 (§5A.2). 카드 왼쪽 위에 순위 번호를 표시한다 |
| F2-3 | 장소 상세(07, `GET /api/places/{placeId}`): 사진, 대분류·중분류 칩, 한 줄 소개, 방문 정보(운영 중 여부와 입장마감 시각, 운영시간, 정기 휴무, 입장 요금 연령별), 장소 소개(더보기), 위치 및 주변 교통, 찜 하트. 사진 출처 문구("한국관광공사 이미지를 사용하였습니다.")를 표시한다. **평점(★)·리뷰는 공공 데이터 소스가 없어 표시하지 않는다** (Figma 현행 상세 화면도 같음) |
| F2-4 | 방문 예정일이 휴무일이면 경고를 표시한다 |
| F2-5 | 장소명·설명은 사용자 언어의 TourAPI 다국어 서비스 데이터를 쓴다. 없으면 영어 → 한국어 순으로 대체 |
| F2-6 | 카테고리 탭은 "전체"와 선택한 테마의 카테고리로 구성한다 (예: 전체 / 음식 / 문화관광 / 자연관광 / 쇼핑). 탭별로 따로 순위를 매긴다 |
| F2-7 | 장소 이름 검색창("장소 이름으로 검색")으로 후보를 검색한다. 정렬은 추천순 고정이다 (Figma에 정렬 토글 없음). 가까운 순·인기순 토글은 필요하면 추가한다 |
| F2-8 | 카드 표시: 순위, 사진(원본 비율), 대분류 · 중분류 칩, 이름, "숙소에서 N.Nkm · 직선거리", 추천 이유 태그(최대 2개, §5A.4), 담기/담김 버튼. 운영 상태·입장료는 카드가 아니라 상세에서 보여준다 |
| F2-9 | **방문자 수를 표시할 때는 출처가 있는 값만 표시**한다. Figma 카드 태그는 "일본인 인기 지역", "외국인 입장객 상위"처럼 숫자 없는 표현이므로, 근거 통계(장소 단위 또는 지역 단위)가 있을 때만 만든다. 통계가 없는 장소에 숫자나 태그를 만들어 표시하지 않는다 |
| F2-10 | 하단 바에 "N곳 선택 · 권장 9~15곳"과 진행 막대, 버튼 "N곳으로 동선 만들기 →"를 둔다. 권장 = 여행 일수 × 3~5곳이고 하루 최대 6곳이다 (§F3-1). 일정 일수 안내 카드: "3일 일정에는 9~15곳을 추천해요. 하루 최대 6곳까지 넣을 수 있어요." 선택이 권장보다 적어도 진행할 수 있으며, 부족분은 추천 순으로 자동으로 채우는 옵션을 둔다 `[결정 필요: Q11]` |
| F2-11 | 한 페이지에 5곳을 보여준다. 숫자 페이지네이션(처음/이전/번호/다음/마지막)을 쓴다. 후보가 부족하면(반경 내 후보 5개 미만 등) 다른 카테고리·거리 확대를 안내한다 |
| F2-12 | 담기 상태는 동선 만들기 요청(`POST /api/trips/{tripId}/route`)에 장소 목록으로 담아 보낸다. 장소 선택만 따로 저장하는 API는 없다 |
| F2-13 | "함께 가기 좋은 곳" 정렬(연관 관광지)은 Figma에 없어 후순위다 |

### F3. 동선 설계
Figma 「03 동선」(프레임 이름이 "02c 장소 선택"으로 중복됨), 「03a 지도로 보기」, 「계획 확인」 기준이다. 일자별 일정은 `GET /api/trips/{tripId}/days/{dayNumber}`로 받는다.

| ID | 요구사항 |
|---|---|
| F3-1 | 하루 최대 6곳. 날짜별 지역 묶기 → 가까운 곳 순서 → 2-opt 개선 → 식사 삽입 → 운영시간 검사 순으로 배치한다 (§5A.5~5A.8, 최적해 보장 안 함). 동선 만들기는 `POST /api/trips/{tripId}/route` |
| F3-2 | 일자 화면 상단에 시간대("09:40 - 19:00")와 요약("장소 4곳 · 숙소 왕복 포함 총 이동 2시간 5분"), "이날 대중교통 예상 1인 ₩6,100 · 경비에 반영"을 표시한다. **구간별 이동수단·운임 카드는 Figma에 없다.** 구간 값(시간·운임)은 계산해 저장하고 경비에 쓴다 (ODsay) |
| F3-3 | 장소 카드에 도착~출발 시간과 "체류 1시간 30분"을 표시한다. 드래그로 순서를 바꾸면 "순서를 바꾸면 이동시간과 운임을 다시 계산해요" 안내대로 재계산한다 (`PUT .../days/{dayNumber}/order`). 장소를 삭제할 수 있다 (`DELETE .../items/{itemId}`). 장소 추가는 Figma에 API가 없다 (§2.2) |
| F3-4 | 오프라인에서 순서를 바꾸면 해당 구간을 "재계산 필요" 상태로 표시하고, 온라인이 되면 갱신한다 |
| F3-5 | 운영시간 밖 방문, 휴무일 방문은 경고 배지로 표시한다 |
| F3-6 | 각 일자의 **출발·복귀 지점은 숙소**다 ("숙소 왕복 포함"). 첫 장소까지와 마지막 장소에서 숙소로 돌아오는 구간도 이동 시간·운임에 포함하고 교통비에 반영한다 (§5A.6, §5.5) |
| F3-7 | 일자 탭으로 날짜를 바꾼다. 각 일정은 `GET .../days/{dayNumber}` 응답으로 그린다 |
| F3-8 | 지도로 보기(03a): 네이버 지도 영역에 숙소와 1~N번 마커를 방문 순서대로 직선으로 잇는다. "목록·지도" 전환, 하단에 "N일차 · 장소 N곳 · 시간대"와 "숙소 왕복 포함 총 이동 시간 · 방문 순서대로 이었어요" 요약, "목록으로" 버튼. 지도 SDK는 `[결정 필요: Q8]` |
| F3-9 | 하단 네비의 "계획 확인"과 "지도" 탭은 지금 여행(`GET /api/trips`의 진행 중·예정 여행)의 일자 일정을 같은 화면 구성으로 보여준다. 이전 여행 기록은 마이페이지(F12)에서 본다 |
| F3-10 | 동선 하단에서 예상 경비(F4)로 이동한다 |

### F4. 예상 경비
세부 계산 로직은 §5를 따른다.

| ID | 요구사항 |
|---|---|
| F4-1 | 총액 카드: **중간값을 크게**, 그 아래 한 줄로 범위("보통 ₩a ~ ₩b")를 표시한다 |
| F4-2 | 알뜰/보통/여유 토글. 기본값은 "보통" `[결정 필요: 온보딩에서 묻기 여부]` |
| F4-3 | 1인 기준/전체 기준 토글. 전체 = 1인 × 인원 |
| F4-4 | 희망 예산 비교: 설정 예산, 예상 필요 경비, 초과/여유 금액과 안내 문구 |
| F4-5 | 항목 카드 5개: 식비, 쇼핑, 관광·입장료, 교통, 기타. 각 카드에 근거 배지(`통계 기반` / `일정에서 계산` / `테마 반영`)를 붙인다 |
| F4-6 | 배지 또는 "근거 보기"를 누르면 출처 시트: 데이터셋명, 조사 연도, 표본 수, 대체(fallback) 여부, 계산 방식, 한계 문구 |
| F4-7 | 일자별 예상 지출: 날짜별 차이는 계산 항목(입장료, 대중교통)에서만 생긴다. 통계 항목은 일수로 균등 배분한다 |
| F4-8 | 금액은 사용자가 설정(F7)에서 고른 **표시 통화 한 개**로 보여준다. 서버가 요청 헤더 `X-Currency`를 보고 원화 금액을 환산한다. 환율 기준일을 표시한다. (기존 "원화 + 자국 통화 병기"는 Figma 설정 화면 기준으로 폐기) |
| F4-9 | 화면 내 모든 수치는 하나의 추정 응답(`GET /api/trips/{tripId}/cost-estimate`)에서 나온다. 화면별로 따로 계산하지 않는다 |
| F4-10 | "이 일정으로 확정"을 누르면 `POST /api/trips/{tripId}/confirm`으로 여행을 확정하고 상태를 "진행 예정"으로 바꾼다. 확정된 여행은 홈의 "나의 여행" 카드와 계획 확인 탭에 나타난다 |

> Figma 「04 예상 경비」는 단일 금액이고 범위·토글·근거 배지·출처 시트가 없으며, "숙박" 항목이 있어 숙박 제외 기준과 충돌한다. 이 절의 요구사항(F4-1~F4-7)은 Figma를 고치기 전까지 유지한다 (§10).

수용 기준:
- 항목별 중간값 합계 = 총액 중간값 (v1 기준, §5.5)
- 1인 평균 × 인원 = 전체 기준 총액
- 표시 통화 총액 = 원화 총액 × 환율 (반올림 오차 1단위 이내)

### F9. 번역 (사진·음성)
> **Figma 2026-10-28 기준 번역 화면과 API가 없다.** 아래 내용은 v1.2 결정을 유지한 것이며, MVP에 계속 넣을지 Figma에 반영할지는 팀 확인이 필요하다 (Q16). 서버 API는 `POST /api/translate/text`로 Figma 목록에 추가해야 한다 (§9.5).

방한 외국인이 간판, 메뉴판, 안내문을 읽고 현지인과 말할 수 있게 돕는 기능이다. 처리 방식은 다음과 같다.

```
[사진] 카메라 → 기기 내 OCR(ML Kit) → 인식 텍스트 ─┐
                                                    ├─> 서버 번역 프록시 → 번역 API → 결과 표시
[음성] 마이크 → 기기 OS 음성 인식 → 인식 텍스트 ───┘
```
사진과 음성 파일은 서버로 보내지 않고, 인식된 **텍스트만** 서버로 보낸다 (§11).

| ID | 요구사항 |
|---|---|
| F9-1 | 번역 화면은 "사진" / "음성" 두 탭으로 구성한다. 진입점은 홈과 동선 화면 |
| F9-2 | 사진: 카메라 촬영 또는 갤러리 선택. OCR은 한국어 스크립트를 기본으로 실행한다 (한국 간판·메뉴판이 대상). 중국어·일본어 스크립트 인식은 2차 |
| F9-3 | 인식된 텍스트를 줄·블록 단위로 보여주고, 전체 또는 선택한 블록만 번역한다. 번역 API는 1회 최대 5,000자이므로 초과 시 나눠서 호출한다 |
| F9-4 | 결과는 원문과 번역을 함께 표시하고 "기계 번역" 라벨을 붙인다 |
| F9-5 | 음성: 방향 토글 "내 언어 → 한국어" / "한국어 → 내 언어". 방향에 따라 음성 인식 언어(ko-KR 또는 사용자 언어)를 바꾼다 |
| F9-6 | "내 언어 → 한국어" 결과는 상대방에게 보여줄 수 있게 큰 글씨 전체 화면 보기를 제공한다. 번역문 읽어주기(TTS)는 선택 기능 `[결정 필요: Q7]` |
| F9-7 | 서버에는 텍스트만 전송한다. 사진·음성은 기기에서 처리 후 폐기하고 서버에 저장하지 않는다. 번역 텍스트도 서버에 저장하지 않는다 (기기 내 최근 20건 캐시는 선택) |
| F9-8 | MVP는 번역을 온라인에서만 제공한다. OCR은 번들 모델로 오프라인 동작이 가능하다. 오프라인 번역(온디바이스 모델)은 2차 |
| F9-9 | 음성 인식이 불가능한 기기·언어이면 안내 문구를 보여주고 텍스트 입력 번역으로 대체한다 |
| F9-10 | 웹 버전에서는 번역 탭을 비활성화하고 앱 설치를 안내한다 (네이티브 모듈 의존) |
| F9-11 | 카메라·마이크 권한 요청 문구는 지원 언어 전부로 작성한다 |

수용 기준(목표치, 유저 테스트 후 재조정):
- 한글 메뉴판 사진 20장으로 OCR → 번역 표시까지 p95 5초 이내 (네트워크 정상)
- 번역 결과에 원문 병기와 "기계 번역" 라벨이 항상 표시된다

번역 엔진은 §7.6의 비교 결과에 따라 **Papago(서버 프록시)를 기본**으로 하고, 온디바이스 번역과 LLM은 2차로 둔다.

### F10. 지도 앱 길 안내 연결
> Figma 「03a 지도로 보기」는 지도 영역을 "네이버 지도 (Dynamic Map)"로 표기했고, "지도 앱으로 길 안내" 버튼과 앱 선택 시트는 확인한 텍스트에 없다. 길찾기 연결은 팀 결정(네이버지도 리디렉션)을 유지하되 버튼 디자인이 필요하다 (§10).

| ID | 요구사항 |
|---|---|
| F10-1 | 동선 화면의 각 장소와 구간에 "지도 앱으로 길 안내" 버튼을 둔다 |
| F10-2 | 네이버 지도 앱 URL Scheme(앱 버전 5 이상)을 우선 사용하고 카카오맵 URL 스킴을 대안으로 제공한다. 기기에 설치된 앱만 선택지로 보여주고, 둘 다 없으면 앱스토어 또는 웹 링크로 안내한다 |
| F10-3 | 앱이 전달하는 정보는 도착지 좌표와 장소명이다. 출발지(현재 위치)는 지도 앱이 처리하므로 KOREADY 앱은 사용자의 현재 위치를 수집하지 않는다 (§11 위치정보 항목과 Q3 참고) |
| F10-4 | 앱 안에서 표시하는 대중교통 시간·운임은 ODsay 결과다 (경비 계산용). 길 안내는 지도 앱이 맡는 것으로 역할을 분리한다 |
| F10-5 | 두 앱의 URL 스킴 파라미터는 각 공식 문서로 확인해 구현한다. 카카오는 공식 답변상 목적지 지정 길찾기가 중심이다. iOS는 설치 여부 확인을 위해 사용할 스킴을 앱 설정에 등록해야 한다 |

### 5.2 기준표(cost band) 생성 — 연 1회 배치
원자료: 서울관광재단「2019~2025년 서울관광 실태조사 통합 Raw Data」

1. 2024년 이후 응답만 사용한다 (물가 반영).
2. 서울 체류일수가 0 이하인 응답은 제외한다.
3. 항목별 1인 1일 지출 = 항목 지출 ÷ 서울 체류일수.
4. 항목별로 상·하위 0.5%를 경계값으로 대체한다 (재단 보고서 방식과 동일).
5. 국적 권역 × 항목별로 가중 분위수 p25(알뜰), p50(보통), p75(여유)를 구한다. 가중치 컬럼이 있으면 사용한다.
6. 권역 표본이 30명 미만이면 전체(ALL) 값으로 대체하고 `fallback=ALL`을 기록한다.
7. 결과를 `cost_band`에 새 버전으로 적재한다. 기존 버전은 삭제하지 않는다.

구현: `build_cost_bands.py` (숙박 제외, 총액 분위수 행 추가를 반영해 갱신 예정)

### 5.3 최신성 보정 — 월 1회 배치
- 한국관광 데이터랩의 국적별 월간 카드소비에서 "조사 기간 평균 대비 최근 3개월 평균" 비율을 구해 `trend_adjustment`로 저장한다.
- 보정 계수는 0.8~1.3으로 제한한다 (이상치 방지).
- 출처 시트에 보정 적용 사실과 기준 월을 표시한다.

### 5.4 수준(level) 결정
```
base_level = 토글 값 (알뜰=p25, 보통=p50, 여유=p75)
item_level = base_level
if 항목이 선택 테마와 연결됨: item_level = min(item_level + 1단계, p75)
```

| 테마 | 한 단계 올리는 항목 |
|---|---|
| 음식 | food |
| 쇼핑 | shopping |
| 역사 관광 | attraction (통계 사용 시에만) |
| 문화 관광 | attraction (통계 사용 시에만) |
| 체험 관광 | attraction (통계 사용 시에만) |
| 레저 스포츠 | attraction (통계 사용 시에만) |
| 축제/공연/행사 | attraction (통계 사용 시에만) |
| 자연관광 | 없음 |

### 5.5 항목 금액 (1인 기준)
```
days = 여행 일수 (N박 M일의 M)
adj  = trend_adjustment

통계 항목 (food, shopping, etc):
  amount[level] = band[region][item][level] × days × adj

attraction:
  동선 내 입장료가 1개 이상 확인되면  → 입장료 합계 (계산값, 세 수준 동일)
  요금 정보가 없는 장소는 "요금 정보 없음"으로 표시
  입장료가 하나도 없으면             → 통계 항목과 같은 방식

transport:
  transit = 동선 구간 대중교통 운임 합계 (계산값, 숙소 출발·복귀 구간 포함)
  stat    = band[region][transport][level] × days × adj
  amount[level] = transit + max(0, stat − transit)
  └ 두 번째 항은 "택시 등 여유분"으로 카드에 분리 표시

총액[level] = Σ 항목 amount[level]      (v1)
```
- v1의 총액 범위는 항목별 분위수 합이라 실제 총지출 분위수보다 넓다. 출처 시트에 명시한다.
- v1.1에서 응답자별 총액 분위수(`item='total'`)로 총액 범위를 계산한다.

### 5.6 인원, 일자, 통화
- 전체 기준 = 1인 기준 × 인원. 공유 비용(택시 합승 등)은 v2에서 다룬다.
- 일자별 금액 = (통계 항목 ÷ days) + 그날의 계산 항목(입장료, 운임).
- 표시 통화 금액 = 원화 × 환율. 언어·통화는 서버에 저장하지 않으므로(F7-5) 요청 시점의 최신 환율을 쓰고 환율 기준일을 응답에 담는다.

### 5.7 계산 위치
- 확정 비용(운임, 입장료)은 동선 저장 시 서버가 계산해 `trip_item`에 저장한다.
- 합산(수준, 테마, 인원, 통화)은 **서버와 클라이언트가 같은 로직**으로 수행한다. 서버 값이 기준이고, 오프라인일 때만 클라이언트 값을 쓴다.
- 기준표는 버전 단위로 앱에 내려받는다.

### 5.8 화면에 표시하는 한계 문구
- 설문 응답 기반 추정이며 개인 지출과 다를 수 있습니다.
- 숙박비와 항공권은 포함하지 않습니다.
- 총액 범위는 항목별 범위를 합한 값이라 실제보다 넓게 나올 수 있습니다. (v1)
- 표본이 적은 국적은 전체 방문객 평균을 사용했습니다. (fallback 시)

## 5A. 추천·동선 알고리즘

### 5A.1 원칙
- MVP에서는 **머신러닝 학습을 하지 않는다.** 출시 전에는 학습에 쓸 사용자 행동 데이터가 없고, 학습 모델은 추천 이유를 설명하기 어려워 "모든 추천에 근거 명시"라는 핵심 가치와 맞지 않는다.
- 대신 공공 통계를 **가중치 점수 모델**과 **제약 조건 경로 휴리스틱**에 입력으로 쓴다. 모든 가중치와 기본값은 설정 파일로 관리해 코드 수정 없이 조정한다.
- LLM은 숫자와 순서를 결정하지 않는다. 쓰더라도 설명 문장 다듬기 같은 보조 역할로 한정한다 (§5A.10).

### 5A.2 장소 추천 점수

**① 후보 필터**
다음 중 하나라도 해당하면 후보에서 제외한다.
- 장소가 서울이 아님 (MVP 서비스 범위)
- 선택 테마의 분류 매핑(아래 표)에 해당하지 않음
- 여행 기간 전체가 휴무
- 좌표 없음

| 테마 (Figma) | TourAPI 분류체계 매핑 초안 (`lclsSystm`, 정의서 기준. 설정 파일 `theme_map.json`으로 관리) |
|---|---|
| 음식 | 음식 `FD` 중 한식 `FD01`, 외국식 `FD02`, 간이음식 `FD03`, 주점 `FD04`, 카페/찻집 `FD05` (`FD04`는 제외 검토 중. 결정 전까지 포함) |
| 쇼핑 | 쇼핑 `SH` 중 백화점 `SH01`, 쇼핑몰 `SH02`, 면세점 `SH04`, 전문매장/상가 `SH05`, 시장 `SH06` (`SH04`는 사후면세점 4,104건이 섞여 있어 제외를 제안 중. 결정 전까지 포함, 추천 설계 §12-3) |
| 역사 관광 | 역사관광 `HS` 전체(역사유적지 `HS01`, 역사유물 `HS02`, 종교성지 `HS03`) |
| 문화 관광 | 문화관광 `VE` 중 랜드마크 `VE01`, 테마공원 `VE02`, 전시시설 `VE07`, 교육시설 `VE09`, 문화시설(콘텐츠타입 14) |
| 자연관광 | 자연관광 `NA`, 문화관광 중 도시공원 `VE03` |
| 체험 관광 | 체험관광 `EX` |
| 레저 스포츠 | 레저스포츠 `LS` |
| 축제/공연/행사 | 축제·공연·행사 `EV` (기간이 지난 행사는 후보에서 제외, 여행 날짜와 겹치는 것만) |

Figma의 테마 8종은 신분류체계 대분류 이름을 그대로 쓴 것이다. 이전 안의 "감성 카페", "인생샷 명소"는 별도 테마에서 빠졌고, 카페(`FD05`)는 음식에 합쳤다. 인생샷 성격은 추천 이유 태그로 다룬다 (추천 설계 §4.4).

- 분류체계는 대분류 10개(`AC` 숙박, `EV` 축제·공연·행사, `EX` 체험관광, `FD` 음식, `HS` 역사관광, `LS` 레저스포츠, `NA` 자연관광, `SH` 쇼핑, `VE` 문화관광, `C01` 추천코스), 소분류 240개이고 정의서가 소분류별로 관광타입(콘텐츠타입 ID)을 연결한다. 예: 문화관광 `VE`는 관광지(12)·문화시설(14)·레포츠(28)·숙박(32)에 걸쳐 있다.
- 위 매핑은 초안이다. 실제 서울 데이터를 적재한 뒤 분류체계별 장소 수와 대표 장소를 확인해 조정한다 (예: `FD04` 주점, `VE03`의 중복 배치).
- 목록 조회는 `lclsSystm1~3`를 요청 파라미터로 받으므로 테마별로 필요한 분류만 수집할 수도 있다.

콘텐츠 유형 ID는 국문 서비스와 외국어 서비스의 값이 서로 다르다 (정의서 기준 국문 → 다국어: 관광지 12→76, 문화시설 14→78, 축제·공연·행사 15→85, 레포츠 28→75, 숙박 32→80, 쇼핑 38→79, 음식점 39→82, 여행코스 25→없음). 콘텐츠 유형 매핑표는 언어별로 따로 둔다.

**② 점수 계산** (추천 장소 순위 화면, F2)
```
score = 0.30 × theme        카테고리(테마) 적합도 (0~1)
      + 0.30 × popularity   방문자 수 기반 인기도 (0~1)
      + 0.25 × distance     숙소와의 거리 점수 (0~1)
      + 0.15 × quality      정보 완성도 (0~1)
```
가중치는 시작값이며 설정 파일로 관리한다 (§5A.11로 조정). Figma 「02c」에는 정렬 토글이 없어 화면은 추천순으로 고정한다 (F2-7). 아래 정렬 방식은 토글을 추가할 경우의 정의이며, 숙소 미정 시에는 선택한 지역 중심을 숙소로 쓴다.

| 정렬 | 방법 |
|---|---|
| 추천순 (기본) | 위 가중합 |
| 가까운 순 | distance 내림차순, 동점이면 score |
| 인기순 | popularity 내림차순, 동점이면 score |

| 요소 | 정의 |
|---|---|
| theme | 사용자가 고른 테마 중 이 장소의 분류와 매핑되는 테마 수 ÷ 고른 테마 수. 카테고리 탭에서는 해당 탭의 분류에 속하면 1 |
| popularity | 아래 ③·④ 방법으로 구한 값을 후보 내 최대값으로 나눈 값 |
| distance | `exp(−d ÷ 5)`. d는 숙소와 장소의 **직선거리(km)**, 5는 감쇠 거리(설정값). 1km 0.82, 3km 0.55, 5km 0.37, 10km 0.14. 인기 있는 곳이 멀어도 상위에 오를 수 있도록 지수 감쇠를 쓴다 |
| quality | 사진, 운영시간, 입장료(해당 시), 사용자 언어 설명의 보유 여부를 각 0.25로 합산 |

- 거리는 순위 계산에서는 직선거리만 쓴다. 후보 수백 개에 대해 ODsay를 호출하지 않기 위해서다. 화면에는 "직선거리"라고 표시하고 실제 이동시간·운임은 동선 확정 후 구간별로 보여준다 (§5A.7).
- **연관 방문 점수(related)는 초기 순위에서 뺀다.** 연관 관광지는 "이미 고른 장소"가 있어야 계산되기 때문이다. 사용자가 장소를 고른 뒤 "함께 가기 좋은 곳" 정렬(F2-13, 후순위)에서만 `score_related = 0.9 × score + 0.1 × related`로 쓴다.
- 숙소를 아직 정하지 못해 권역을 선택한 경우 권역 대표 좌표를 숙소로 본다.

**③ 국적별 인기도 보정 (소표본 보정)**
```
pop_raw(r, a) = (방문자수(r, a) + m × 방문비율(ALL, a)) ÷ (응답자수(r) + m)
  r: 국적 권역, a: 방문지(지역), m = 50 (보정 강도, 설정값)
```
- 표본이 적은 권역일수록 전체 방문객 비율 쪽으로 당겨진다.
- 서울관광 실태조사의 방문지가 지역 단위(예: 명동, 홍대)이면, 그 지역 경계 또는 반경 안에 있는 장소가 같은 값을 공유한다. 방문지 변수의 단위는 코드표로 확인 후 확정한다.

**④ 방문자 수 반영 (장소 단위 통계가 있을 때)**
```
region_pop = ③에서 구한 국적별 지역 인기도 (지역을 공유하는 모든 장소에 상속)
place_pop  = 장소 단위 외국인 입장객·방문객 수의 서울 내 백분위 (0~1). 통계가 없으면 없음
popularity = 0.6 × region_pop + 0.4 × place_pop     (place_pop이 있을 때)
           = region_pop                              (없을 때)
```
- 장소 단위 통계 후보: 서울시 주요관광지점 입장객(4대궁·종묘, 박물관·전시관, 자치구별), 한국문화관광연구원 관광자원통계서비스. 무료 명소·음식점·쇼핑은 장소 단위 통계가 없으므로 지역 값을 상속한다.
- 지역 ↔ 장소 매핑표(예: 명동·남대문시장 지역에 속하는 TourAPI 장소 목록)는 팀이 직접 만든다. 서울 주요 20~30개 지역부터 시작한다.
- 화면에 방문자 수를 표시하는 규칙은 F2-9를 따른다.

### 5A.2a 후보 풀과 거리 계산 (DB 우선, `locationBasedList2`는 보조)
숙소 좌표를 입력받아 가중치로 순위를 매길 때, 후보와 거리는 **우리 DB에서 계산**한다. TourAPI의 위치기반 조회(`locationBasedList2`)를 사용자 요청마다 호출하지 않는다 (rule.md R-C50, R-K14).

| 비교 | DB 계산 (채택) | 요청 시 `locationBasedList2` 호출 (미채택) |
|---|---|---|
| 호출 한도 | TourAPI 호출 없음. 배치 수집만 사용 | 사용자당 관광타입 5개 × 페이지 수만큼 호출, 개발계정 일 1,000건에 쉽게 도달 |
| 반경 | 서울 전체를 후보로 두고 거리는 점수로 반영(지수 감쇠) | 반경 최대 20,000m. 서울은 동서로 약 30km라 숙소가 한쪽 끝이면 반대편 명소가 빠짐 |
| 정보 | 이용시간·입장료·개요를 미리 적재 | 응답에 이용시간·요금·개요가 없어 상세 호출이 추가로 필요 |
| 응답 속도 | DB 조회 | 외부 API 지연에 좌우됨 |

**거리 계산 (순위용)**
```sql
-- 숙소 좌표(:lat, :lng) 기준 후보와 직선거리(km). 위경도 범위로 먼저 줄이고 하버사인으로 계산
SELECT content_id, content_type, lcls3, sigungu_cd,
       2 * 6371 * asin(sqrt(
         power(sin(radians(lat - :lat) / 2), 2) +
         cos(radians(:lat)) * cos(radians(lat)) *
         power(sin(radians(lng - :lng) / 2), 2))) AS dist_km
FROM place
WHERE is_visible
  AND lcls3 = ANY(:theme_lcls3_list)
  AND lat IS NOT NULL AND lng IS NOT NULL
```
- 숙소 좌표는 소수 3자리(약 100m)로 반올림해 저장하므로(§11) 거리 오차는 거리 점수에 영향이 없다.
- `distance` 점수는 `exp(−dist_km ÷ 5)`를 그대로 쓴다 (§5A.2).
- PostGIS를 쓰면 공간 인덱스로 더 빠르게 할 수 있으나 필수는 아니다. 서울 장소는 수만 건 이하라 위경도 인덱스와 하버사인으로 충분하다 `[추정, 적재 후 건수로 확인]`.

**`locationBasedList2`를 쓰는 곳 (보조)**

| 용도 | 방법 |
|---|---|
| DB 누락 점검 | 권역 칩 대표 좌표 10곳 안팎에서 반경 5km를 관광타입별로 조회해 DB의 같은 반경 결과와 비교. 주 1회 배치 (§13) |
| 누락 장소 보충 | 점검에서 DB에 없는 `contentid`가 나오면 `place`에 추가하고 상세를 적재 대기열에 넣음 |
| 반경 결과 캐시 | 숙소 좌표(100m 반올림)와 관광타입을 키로 24시간 캐시. 같은 숙소를 여러 사용자가 입력해도 재호출하지 않음 |
| 현재 위치 기반 "지금 근처" | 현재 위치 기능을 넣기로 하면(Q3) 사용. 위치정보법 검토 선행 |

**호출 파라미터 권장값**
- `mapX` = 경도, `mapY` = 위도 (대문자 X, Y). 응답은 `mapx`, `mapy`(소문자)
- `radius` = 5000(m)에서 시작, 후보가 적으면 10000 → 20000으로 확대. 최대 20000
- `lDongRegnCd` = 11 (반경이 경기도로 넘어가도 서울만 받음)
- `contentTypeId` = 12, 14, 28, 38, 39를 따로 호출 (숙박 32는 숙소 검색 용도). 테마가 정해져 있으면 `lclsSystm1`로 호출 수를 줄임
- `arrange` = `E`(거리순). `S`(거리순, 대표 이미지가 있는 장소만)는 사진 없는 장소를 빼므로 쓰지 않음. 사진이 없는 장소는 정보 완성도 점수로만 낮춤
- 응답의 `dist`는 숙소 좌표 기준 직선거리(미터, 문자열). 매뉴얼 예시 `676.69...`. 실제 단위와 정렬은 프로파일러로 확인 (§13)

### 5A.3 다양성 보정
"전체" 탭에서만 적용한다. 점수 순으로 한 곳씩 뽑을 때마다, 남은 후보 중 같은 세부 분류의 점수에 0.8을 곱한다. 카테고리 탭은 탭 안에서 따로 순위를 매기므로 보정하지 않는다. 목록은 5곳씩 페이지로 반환한다 (F2-11, API 20).

### 5A.4 추천 이유 태그
점수에 가장 크게 기여한 요소 상위 2개를 태그로 표시한다.

| 요소 | 태그 문구 예 |
|---|---|
| theme | "쇼핑 테마", "역사·문화 테마" (선택한 테마 이름 기반) |
| popularity | "일본인 방문객이 많이 찾는 곳" |
| distance | "숙소에서 1.2km" |
| related | "선택한 ○○와 함께 많이 방문" |
| quality | 태그로 쓰지 않음 |

### 5A.5 날짜별 지역 묶기
0. 숙소는 모든 날의 출발·복귀 기점이다. 군집 중심과 숙소의 거리는 참고값으로만 쓰고, 군집 수는 여행 일수와 같게 유지한다.
1. 사용자가 담은 장소들을 좌표 기준으로 `k = 여행 일수` 개 군집으로 묶는다 (k-means, 초기값 고정 시드).
2. 한 군집이 6곳을 넘으면 군집 중심에서 가장 먼 장소를 가장 가까운 다른 군집으로 옮긴다. 모든 군집이 6곳 이하가 될 때까지 반복한다.
3. 군집을 날짜에 배정할 때 휴무일 충돌이 가장 적은 배정을 고른다 (일수가 7일 이하이므로 전수 비교 가능).

### 5A.6 하루 순서 정하기
```
0. 기점: 숙소에서 출발한다 (출발 시각 기본 09:00, 설정값).
1. 첫 장소: 그날 장소 중 운영 시작이 가장 이른 곳. 같은 시간대에 여럿이면 숙소에서 가까운 곳
2. 초안: 현재 위치에서 추정 이동시간이 가장 짧은 다음 장소를 반복 선택 (최근접 이웃)
3. 개선: 2-opt — 경로의 두 구간을 뒤집어 총 이동시간이 줄면 교체, 개선이 없을 때까지 반복
4. 식사 삽입: 11:30~13:30, 17:30~19:30 사이에 직전 장소 반경 800m 내 음식점 후보를 1곳씩 삽입
   (사용자가 이미 음식점을 담았다면 그 장소를 식사 시간대로 이동)
5. 시각 계산: 도착 시각 = 이전 출발 시각 + 이동시간, 출발 시각 = 도착 + 머무는 시간
6. 제약 검사: 운영시간 밖 도착·휴무일이면 같은 날 안에서 순서를 한 칸씩 옮겨 재검사,
   해결되지 않으면 경고 배지 (F3-5)
7. 복귀: 마지막 장소에서 숙소로 돌아오는 구간을 추가한다 (F3-6)
```

### 5A.7 이동시간 계산 (2단계)
| 단계 | 방법 | 목적 |
|---|---|---|
| 순서 결정 중 | 직선거리 × 1.3(우회 계수) ÷ 평균 속도. 1km 이하는 도보 4km/h, 초과는 대중교통 18km/h + 대기 8분 | 즉시 계산, 외부 호출 없음 |
| 순서 확정 후 | 확정된 구간만 ODsay 호출 → 실제 이동수단, 소요시간, 운임 저장. 구간에는 **숙소→첫 장소, 마지막 장소→숙소**가 포함된다 | 정확한 시간·교통비 |

계수와 속도는 설정값이며, ODsay 결과와 비교해 주기적으로 보정한다. 이 방식으로 외부 API 호출을 "모든 장소 쌍"이 아니라 "확정 구간 수"로 줄인다. 하루 6곳이면 구간은 최대 7개(장소 간 5 + 숙소 왕복 2)다. 같은 구간 결과는 DB에 저장해 재사용한다.

### 5A.11 초기 가중치 조정 방법
- 국적 2개(일본, 중국) × 테마 조합 5개 × 일수 2종 = 샘플 일정 20개를 생성한다.
- 팀원이 "다닐 만한가 / 테마에 맞는가 / 이동이 과한가"를 1~5점으로 평가한다.
- 평균 3.5점 미만 항목과 관련된 가중치·기본값을 조정하고 결과를 설정 파일 변경 이력으로 남긴다.

데이터별 주의사항:
- 한국관광공사 서비스 주소는 `...Service1`에서 `...Service2`로 변경되었다(공공데이터포털 공지). 구버전을 호출하면 서비스 폐기 오류가 난다는 개발 사례가 있으므로 블로그 예제를 그대로 복사하지 않는다. 기본 주소는 `https://apis.data.go.kr/B551011/KorService2`.
- TourAPI 응답은 결과가 없으면 `items`가 빈 문자열로 오고, 결과가 1건이면 배열이 아닌 단일 객체로 오는 경우가 있다고 여러 프로젝트가 기록했다. 파싱 코드에서 방어한다.
- Papago Translation API는 글자 수 기준 과금이고 1회 호출당 최대 5,000자다. 요금표는 아직 확인하지 못했으므로 이용 신청 후 콘솔에서 확인한다.
- **트래픽:** 활용신청 매뉴얼 v3.3은 개발계정이 "각 오퍼레이션별 일일 1,000건"이라고 안내한다(활용매뉴얼 v4.4는 "일 1,000건"으로만 표기). 오퍼레이션별 한도라면 목록 1,000회(페이지당 최대 100건 가정 시 이론상 10만 건)와 상세 3종 각 1,000회가 따로 적용되므로 서울 전체 적재는 며칠에 나눠 가능하다. 수집 스크립트는 오퍼레이션별 900회에서 멈춘다. 실제 한도 적용 방식은 첫 대량 호출 때 확인한다.
- **운영계정:** 개발계정 활용신청은 자동승인이고 약 10~30분 뒤 사용 가능하다. 운영계정은 한국관광공사 담당자 승인(약 1~3일)이 필요하며, 개발계정의 호출 이력과 활용 App/Web URL을 확인하고 활용사례로 등록·홍보된다. 승인 후 24개월 사용 가능하며 만료 시 연장 신청한다. 따라서 개발 기간 중에 호출 이력을 쌓고 URL(웹 데모 포함)을 준비해 둔다.
- **지역·분류 체계 변경(v4.4):** 지역코드·서비스분류코드 오퍼레이션이 삭제되었다. 지역은 법정동 코드(`ldongCode2`로 조회, 서울 시도코드 `11`, 시군구 25개), 분류는 분류체계 코드(`lclsSystmCode2`로 조회)를 쓴다. 이전 블로그 예제의 `areaCode`, `cat1~3` 파라미터는 사용하지 않는다.
- **이용시간·휴무일 필드는 타입마다 이름이 다르다(`detailIntro2`):** 관광지(12) `usetime`·`restdate`, 문화시설(14) `usetimeculture`·`restdateculture`, 레포츠(28) `usetimeleports`·`restdateleports`, 쇼핑(38) `opentime`·`restdateshopping`, 음식점(39) `opentimefood`·`restdatefood`. 숙박(32)은 `checkintime`·`checkouttime`. 모두 자유 텍스트이므로 파싱 규칙과 실패 처리가 필요하다.
- **입장료 출처(정정):** 관광지(12)의 소개정보(`detailIntro2`)에는 이용요금 필드가 **없다.** 입장료는 반복정보(`detailInfo2`)의 `infoname`("입 장 료", "관람료" 등)과 `infotext`(자유 텍스트)에서 찾아야 한다. 문화시설(14)은 `usefee`, 레포츠(28)는 `usefeeleports`가 있다. 음식점에는 요금 필드가 없고, 쇼핑(38)에는 입장료 개념의 필드 없이 판매 품목별 가격(`saleitemcost`)만 있다. 숙박(32)의 객실 요금(`roomoffseasonminfee1·2`, `roompeakseasonminfee1·2`)은 소개정보가 아니라 반복정보(`detailInfo2`)에 있다. 따라서 장소 1개를 완성하려면 상세 호출이 최대 3종이다.
- **저작권 유형:** 목록·상세 응답의 `cpyrhtDivCd`에 이미지 저작권 유형(Type1 출처표시, Type3 출처표시+변경금지)이 들어 있다. 화면에는 변형(자르기·필터) 없이 출처와 함께 쓰고, Type3 이미지는 가공하지 않는다.
- 연관 관광지 API도 개발계정 호출 한도가 있으므로 함께 운영계정 신청을 계획한다.
- **위치기반 조회(`locationBasedList2`)는 순위 계산에 쓰지 않는다.** 서울 전체를 DB에 적재하고 거리는 DB에서 계산한다. 이 오퍼레이션은 반경 결과와 DB를 비교하는 누락 점검, 누락 장소 보충, 반경 결과 캐시에만 쓴다 (§5A.2a, rule.md R-K14).
- 연관 관광지 데이터는 차량 내비게이션 기반이고 제공 기간이 한정되어 있다. 가중치를 0.10으로 낮게 둔 이유다.
- 환율 API는 영업일에만 갱신된다. 주말·공휴일에는 직전 영업일 값을 쓰고 기준일을 표시한다.

2차 검토 데이터:
- 서울 열린데이터광장 '서울시 실시간 도시데이터': 주요 장소 혼잡도. "지금 붐비는 곳" 표시용.
- 서울 열린데이터광장 '[단기외국인] 행정동별 서울 생활인구': 외국인 단기 체류자가 많은 지역. 인기도 보조 신호로 검토.

사용하지 않는 데이터:
- 인스타그램 등 SNS 크롤링: 플랫폼 이용약관 위반 및 저작권 문제. 국적별 인기 장소는 실태조사 방문지 집계로 대체한다.

출처 표시: 모든 화면의 출처 시트와 앱 정보 화면에 TourAPI, 서울관광재단, 한국관광 데이터랩, 한국수출입은행을 표기한다. TourAPI 이미지는 공공누리 유형별 이용 조건을 확인한 뒤 사용한다.

## 7. 시스템 구성과 배포

### 7.1 전체 구성
```
[앱: Expo(React Native)]      [웹: 같은 코드의 웹 빌드 → Vercel]
          │                               │
          └──────────── HTTPS ────────────┘
                          │
              [EC2: Nginx + Spring Boot]  ← 배치(@Scheduled) 포함
                  │            │
                  │            └─> 외부 API: TourAPI / ODsay / 연관 관광지 / 환율 / Papago 번역
                  │
                  ├─> RDS PostgreSQL (EC2에서만 접근)
                  ├─> Parameter Store 또는 Secrets Manager (API 키)
                  └─> S3 (선택: 리포트 이미지)
[로컬 실행] build_cost_bands.py → 결과를 RDS에 적재 (연 1회)
```

### 7.2 기술 선택
| 영역 | 선택 |
|---|---|
| 앱 | Expo (React Native), NativeWind, react-native-maps, i18n 라이브러리 |
| 웹 | Expo 웹 빌드(react-native-web), Vercel 배포 |
| 서버 | Spring Boot (REST, JSON), Nginx 리버스 프록시 |
| DB | PostgreSQL (AWS RDS, 서울 리전 ap-northeast-2) |
| 배치 | Spring `@Scheduled` (TourAPI·환율·보정 계수). 필요 시 EventBridge Scheduler로 분리 |
| 인증 | Spring Security + JWT (액세스 30분·리프레시 14일, 회전). 아이디·비밀번호와 Google·Apple OAuth (F11) |
| 푸시 | Expo Notifications (FCM / APNs) |
| 번역·OCR·음성 | OCR: ML Kit Text Recognition v2(기기 내). 음성 인식: `expo-speech-recognition`(OS 엔진 사용). 번역: Papago Translation API(서버 프록시). 모두 네이티브 모듈이라 EAS 개발 빌드가 필요하다 |
| 지도 앱 연동 | 네이버 지도·카카오맵 URL 스킴 (`Linking`) |
| 디자인 | Figma |

### 7.3 Supabase를 쓰지 않는 이유
Supabase의 핵심 장점인 "DB를 서버 없이 바로 API로 쓰기", 인증, 실시간 기능은 이 서비스에 필요하지 않다. 경비 계산, 외부 API 프록시, 배치 같은 서버 로직이 핵심이므로 Spring 서버 + RDS 구성이 설계와 맞는다.

| Supabase 기능 | 대체 |
|---|---|
| PostgreSQL | RDS for PostgreSQL |
| 자동 REST API | Spring Boot API |
| Auth | Spring Security + JWT 직접 구현 (F11) |
| Storage | S3 (선택) |
| 스케줄 작업 | Spring `@Scheduled` |

### 7.4 AWS 운영 원칙 (학생 팀 최소 비용)
- EC2 소형 인스턴스 1대, RDS 최소 인스턴스 단일 AZ로 시작한다.
- **NAT Gateway와 RDS Multi-AZ는 쓰지 않는다** (고정비가 크다).
- HTTPS는 ALB 대신 EC2의 Nginx + Let's Encrypt 인증서로 처리한다.
- RDS는 보안 그룹으로 EC2에서만 접근을 허용한다.
- ODsay 서버 키에 등록할 수 있도록 EC2에 탄력적 IP를 붙인다.
- 가입 직후 AWS Budgets 알림(예: 월 30달러)을 설정한다.
- 2025년 7월 15일 이후 만든 계정은 크레딧 기반 무료 플랜이다. 무료 플랜은 6개월 또는 크레딧 소진 시 만료되고, 유료 전환하지 않으면 유예 기간 후 계정과 리소스가 삭제된다. 발표 이후에도 운영하려면 만료 전에 유료 플랜으로 전환한다.

### 7.5 앱·웹 배포 전략
| 단계 | Android | iOS | 웹 |
|---|---|---|---|
| 개발 중 | EAS 개발 빌드 (OCR·음성 인식이 네이티브 모듈이라 Expo Go 불가) | EAS 개발 빌드 (실기기 설치에는 애플 개발자 계정이 필요할 수 있음, Q6) | 로컬 실행 (번역 탭 제외) |
| 팀·유저 테스트 | EAS로 APK 빌드 후 링크 배포 (무료) | TestFlight (애플 개발자 계정 필요) `[결정 필요: Q6]` | Vercel 미리보기 배포 |
| 정식 공개 | 구글 플레이 (개발자 등록 1회 25달러, 비공개 테스트 후 출시) | 앱스토어 (연 99달러, 심사) | Vercel 운영 배포 |

- EAS 무료 플랜은 현재 표기 기준 월 Android 15회, iOS 15회 빌드에 낮은 우선순위 대기열이다. 네이티브 모듈을 추가할 때마다 개발 빌드를 다시 만들어야 하므로 모듈은 초기에 한꺼번에 정하고, 부족하면 로컬 빌드(`eas build --local`)를 병행한다.
- ML Kit iOS 프레임워크는 최신 Xcode의 iOS 시뮬레이터(arm64)를 지원하지 않는다는 보고가 있다. 번역 기능은 실기기 또는 Android 에뮬레이터에서 테스트한다.
- 웹 버전의 용도: 발표 데모(설치 없이 링크로 체험), 여행 전 계획, 구글 플레이를 쓰기 어려운 중국 사용자 대응.
- 개인정보처리방침 페이지를 Vercel 웹에 올려 스토어 제출 시 URL로 사용한다.
- `react-native-maps`는 웹을 지원하지 않는다. 지도 컴포넌트는 처음부터 플랫폼별 파일(`Map.native.tsx` / `Map.web.tsx`)로 분리한다.

### 7.6 지도 SDK·길 안내·번역 엔진 결정 근거

#### (1) 지도 SDK 언어 지원 확인 결과 (공식 문서·운영진 답변, 2026-09-29 조사)
| | 네이버 | 카카오 |
|---|---|---|
| 웹 지도 | 공식 튜토리얼에 `language` 설정으로 한국어·영어·중국어·일본어 지원 | 공식 문서에 언어 지원 항목 없음 |
| 모바일 SDK | Android SDK에 `setLocale`, `NaverMapOptions.locale` 존재(기본은 시스템 로캘). 단 공식 "Maps 사용 준비" 지원 사양표는 언어를 한국어·영어·일본어로 표기, 비공식 Flutter 래퍼 문서는 4개 언어라고 표기 | 카카오 운영진 답변: SDK는 한국어만 지원, 영문 지원 계획 없음 (2023~2025년 포럼 답변) |
| 정적 지도 | 영어·일본어·중국어 간체 옵션 | 확인 못함 |
| 장소·주소 검색 | Geocoding 다국어 여부 확인 못함 | 영어·중국어 입출력 지원 문의 글이 있으나 답변 미확인 |
| 길찾기 REST API | Directions 5/15: 자동차 길찾기만 | 카카오모빌리티 길찾기 API: 자동차 길찾기 계열만 |
| 길 안내 앱 연동 | URL Scheme (네이버 지도 앱 5 이상) | URL 스킴 (운영진 답변: 목적지 지정 길찾기가 공식 지원 범위) |

결정:
- **카카오 지도 SDK는 제외한다.** 외국인이 보는 화면에 라벨이 한국어로만 나온다.
- **기본은 react-native-maps의 Google 공급자를 유지한다.**
- **네이버는 조건부 후보다.** 모바일 SDK에서 중국어(zh) 라벨이 실제로 표시되는지, 그리고 네이티브(Android/iOS) SDK를 React Native에서 안정적으로 쓸 수 있는지(커뮤니티 래퍼 필요 가능) 스파이크로 확인한 뒤 교체 여부를 정한다 (Q8).
- 네이버·카카오 모두 대중교통 길찾기 REST API가 없으므로 앱 내 대중교통 시간·운임은 ODsay로 계산하고, 실제 길 안내는 두 앱으로 넘긴다 (F10).

#### (2) 번역 엔진 비교
| | Papago (NCP) | ML Kit 온디바이스 번역 | LLM (예: Claude API) |
|---|---|---|---|
| 지원 언어 | 영어·중국어·일본어·스페인어 등 12개국 | 50개 이상 (한·중·일·영 포함) | 다국어 |
| 품질 | 한국어 번역 품질을 강점으로 소개 | 공식적으로 간단한 번역용. 영어를 경유하므로 한↔일 같은 비영어 쌍은 품질 저하 가능 | 맥락 설명 가능, 오역·지연·비용 위험 |
| 오프라인 | 불가 | 가능 (언어 모델당 약 30MB 다운로드) | 불가 |
| 비용 | 글자 수 과금 (요금표 미확인) | 무료 | 토큰 과금 |
| 통합 | 서버 프록시 REST, 키를 서버에 보관 | 커뮤니티 RN 래퍼가 Android만 지원(iOS는 별도 작업) | 서버 프록시 REST |
| 적용 | **MVP 기본** | 2차 (오프라인 대체) | 2차 (메뉴 재료·맵기 설명 등) |

#### (3) OCR·음성 인식
- OCR: ML Kit Text Recognition v2는 중국어·데바나가리·일본어·한국어·라틴 스크립트를 인식하고 기기 안에서 실행된다. Expo용 커뮤니티 래퍼(`rn-mlkit-ocr` 등)가 있으나 유지보수 상태는 확인하지 못했다. 래퍼가 불안하면 Expo 모듈을 직접 작성한다.
- 음성 인식: `expo-speech-recognition`은 iOS·Android의 OS 음성 인식을 감싼다. 개발 빌드가 필요하고, Android 13 이상에서 온디바이스 인식을 쓰려면 해당 언어 모델이 설치되어 있어야 한다.

## 9. API 명세 (Figma 「범례·API 목록」 32개 기준, 2026-10-28)

Figma의 서버 API 목록을 그대로 옮겼다. 번호는 Figma의 API 번호이고, 같은 API는 어느 화면에서든 같은 번호다. 요청·응답 필드는 Figma에 정의되어 있지 않아 §9.3의 예시는 초안이다. 응답은 JSON, 금액 단위는 KRW 정수(표시 통화로 환산되기 전 기준).

### 9.1 공통 규칙

**요청 헤더 (모든 요청)**
- `Authorization: Bearer {accessToken}` — 로그인이 필요한 API
- `Accept-Language: ko | en` — 앱 언어
- `X-Currency: KRW | JPY | USD | EUR` — 표시 통화. 서버가 원화 금액을 환산한다
- 언어·통화 설정은 서버에 저장하지 않는다

**인증 열**: 필요 = 로그인해야 부른다 / 선택 = 로그인하면 더 주는 값이 있다(예: 찜 여부) / - = 로그인 없이

**메서드**: GET 조회, POST 만들기·실행, PUT 고치기, DELETE 지우기

## 11. 보안·개인정보·법적 검토

| 영역 | 요구사항 |
|---|---|
| API 키 | TourAPI·ODsay·환율 키는 AWS Secrets Manager에 보관. 앱 번들에 넣지 않고 서버 프록시로만 호출 |
| 전송 | 모든 통신 HTTPS. API 요청 속도 제한(사용자 ID·IP 기준) |
| 최소 수집 | 회원가입으로 이름, 아이디, 비밀번호(해시), 소셜 계정 식별자를 수집한다. 이메일·전화번호는 Figma 화면에 없어 받지 않는다. 국적은 권역 코드로만 저장 |
| 식별자 | 사용자 ID. 비밀번호는 bcrypt 등 단방향 해시로 저장하고 로그에 남기지 않는다. 로그에 사용자 ID와 일정 상세를 함께 남기지 않음. 토큰은 기기 보안 저장소에 보관 |
| 실제 지출 | 익명 통계 활용은 선택 동의. 국적 권역 × 항목 셀의 표본이 30건 미만이면 집계를 공개하지 않음 |
| 보관 기간 | 회원 탈퇴(`DELETE /api/users/me`) 시 여행·찜·지출 데이터를 삭제한다. 탈퇴하지 않은 계정의 보관 기간은 `[결정 필요]` |
| 공유 | 리포트 공유 이미지는 날짜를 기본으로 숨김 |
| 위치정보 | MVP는 현재 위치 기능 제외를 기본안으로 한다. 포함 시 위치정보법상 위치기반서비스사업 신고 대상 여부 확인 `[결정 필요]`. F10(지도 앱 연결)은 KOREADY 앱이 현재 위치를 수집하지 않고 도착지만 넘기는 방식이라 별도로 볼 수 있으나, 법적 판단은 확인이 필요하다 |
| 고지 | 개인정보처리방침과 동의 문구를 지원 언어 전부로 제공 |
| 숙소 위치 | 사용자가 입력한 숙소 좌표는 소수 3자리(약 100m)로 반올림해 저장하고, 숙소명·상세주소는 서버에 저장하지 않는다(기기에만 보관). 거리 점수와 동선 기점에는 반올림 좌표로 충분하다. 실시간 위치 추적이 아니므로 현재 위치 기능과 구분하되, 위치정보법상 판단은 확인이 필요하다 |
| 번역 데이터 | 사진·음성은 기기에서 처리하고 서버로 보내지 않는다. 서버는 텍스트만 받아 번역 API로 전달하고 저장하지 않으며, 서버 로그에 번역 원문을 남기지 않는다 |
| 음성 인식 엔진 고지 | 기기 OS 음성 인식은 설정에 따라 오디오를 Apple·Google 서버로 보낼 수 있다. 온디바이스 인식을 우선 요청하고, 불가능하면 네트워크 방식이라는 안내를 앱과 개인정보처리방침에 표시한다 |
| 번역 API 남용 방지 | 번역 키는 서버에만 보관하고, 사용자 ID 기준 일일 호출 횟수·글자 수를 제한해 과금 폭주를 막는다 |
| 카메라·마이크 권한 | 번역 기능 진입 시점에 요청하고, 거부해도 다른 기능은 정상 사용 가능. 권한 문구는 지원 언어 전부로 작성 |
| 데이터 이용 조건 | 공공데이터 출처 표시. 원자료 기반 결과를 유료 기능에 쓰기 전 제공 기관 이용 조건 재확인 |
| AWS 계정 | 루트 계정은 팀장만 사용하고 MFA 필수. 팀원은 IAM(또는 IAM Identity Center)으로 필요한 권한만 부여. 액세스 키를 깃허브에 올리지 않음 |
| 앱 서명 키 | Android 업로드 키와 iOS 인증서는 EAS 자격 증명 관리에 보관하고 개인 PC에만 두지 않음 |

| Q9 | 번역 엔진을 Papago로 확정할까? | Q16이 정해진 뒤 결정. 요금표 확인 필요 |
| Q10 | 주소·장소명 검색(`/api/geo/search`)과 좌표→주소(`/api/geo/reverse`) 제공자는? | Figma에 02b-01·02b-03 API가 있으므로 **지오코딩 API가 필요하다.** 카카오 로컬(한국어 주소 중심), 구글(다국어, 유료·약관 확인), 네이버 중 선택 |
| Q11 | 장소 선택에서 최소 선택 수를 강제할까? | Figma는 "권장 9~15곳"만 안내. 강제 없음 + 자동 채우기(기본안) / 일수 × 3곳 이상 필수 |
| Q12 | 비밀번호 찾기·재설정은 어떻게 할까? | Figma에 화면이 없고 이메일을 받지 않는다. 소셜 로그인 권장 안내만 / 이메일 수집 추가 |
| Q13 | 알림(01a)을 MVP에 넣을까? | Figma는 "미정(API 없음)". 넣으면 알림 API·저장·푸시 연동 필요 / 제외하면 헤더 종 아이콘 삭제 |
| Q14 | "상관없음" 추천 모드를 화면에 둘까? | Figma 조건 입력에는 모드 토글이 없고, 숙소 미정이면 "지역 중심 기준 가까운 곳부터" 추천한다. 팀 결정(숙소 근처/상관없음 2가지)과 충돌하므로 화면 추가 또는 삭제 결정 (추천 설계 §12) |
| Q15 | 챗봇 카드의 별점·대기시간·예약 가능 표시의 데이터 소스는? | 공공 데이터에 없음. 디자인에서 삭제 / 외부 소스(Google 등) 도입 |
| Q16 | 번역(F9)과 지도 앱 길 안내 버튼(F10)을 Figma에 추가해 MVP에 유지할까? | 유지: 화면·API 설계 필요(`/api/translate/text` 등) / 제외: 개발 기간 확보 |
