# KOREADY 추천 알고리즘 상세 설계 (recommendation_design.md)

버전 v0.2 · 2026-10-28 · `spec.md` v1.6 §5A를 구체화한 초안이다. v0.2는 Figma 최신본(2026-10-28)에 맞춰 테마 8종, 숙소 모드, 화면 표시를 고쳤다 (원본: `_backup_20261028/recommendation_design.md`).
참조 구현: `koready-data/recommend.py`, 설정: `koready-data/config/ranking.json` (아래 수치는 이 구현을 실제로 실행한 결과다).

## 0. 결정 사항 (이번 논의 확정)

| 항목 | 결정 |
|---|---|
| 추천 방식 | 가중치 순위(규칙)가 기본. **MVP는 LLM 없이 동작**한다 |
| LLM | 선택 기능. 끄면 템플릿 문장으로 대체되고 추천 결과는 같다 (§8) |
| 숙소 | 두 모드: **숙소 근처** / **상관없음**. 모드는 가중치와 거리 감쇠만 바꾼다 (§3). **Figma 조건 입력에는 모드 토글이 없고, 숙소를 고르면 `near`, "아직 숙소를 정하지 못했어요"+지역 선택이면 그 지역 중심을 숙소로 본 `near`로 동작한다. 화면에 `any`를 둘지는 팀 결정이다 (§12-1, spec Q14)** |
| 데이터 | 한국관광공사 TourAPI가 기본. 평점·리뷰(Google)는 스파이크 후 결정 |
| 길찾기 | 앱은 ODsay로 구간 시간만 표시하고, 길찾기는 네이버지도로 넘긴다 |

## 1. 전체 흐름

```
입력(국적, 테마, 일정, 인원, 숙소, 모드, 속도)
 → ① 후보 필터 (하드 규칙)
 → ② 점수 계산 (가중합)          ┐ 추천 장소 순위 화면 (F2)
 → ③ 다양성 보정                  ┘
 → 사용자가 장소를 고름
 → ④ 날짜별 묶기 (군집 + 휴무·날씨)
 → ⑤ 하루 순서 (순열 탐색 + 운영시간·체력 제약)     동선 화면 (F3)
 → ⑥ 확정 구간만 ODsay 호출 → 시간·운임 표시
 → ⑦ (선택) LLM 설명 문장
```
숫자와 순서는 ①~⑥이 정한다. LLM은 ⑦과 입력 해석에만 쓴다.

## 2. 입력

| 입력 | 값 | 사용처 |
|---|---|---|
| 국적 권역 | 일본, 중국 등 | 인기도(§4.2), 언어 |
| 테마 | 쇼핑·체험 관광·음식·축제/공연/행사·역사 관광·자연관광·레저 스포츠·문화 관광 (복수, Figma 8종) | 테마 점수, 후보 필터 |
| 모드 | `near`(숙소 근처) / `any`(상관없음) | 가중치·반경 (§3) |
| 속도 | `relaxed` / `normal` / `packed` | 하루 장소 수, 도보·강도 상한 (§6) |
| 숙소 좌표 | 위경도 (소수 3자리 저장). 미정이면 권역 대표 좌표 | 거리, 기점 |
| 일정 | 시작일, 일수 | 요일별 휴무, 날씨 |

## 3. 두 모드

모드는 설정 한 벌(`ranking.json`의 `modes`)만 바꾼다. 나머지 로직은 같다.

| | 숙소 근처 (`near`) | 상관없음 (`any`) |
|---|---|---|
| 가중치 theme / popularity / distance / quality | 0.25 / 0.25 / **0.35** / 0.15 | **0.35 / 0.40** / 0.10 / 0.15 |
| 거리 감쇠 d0 | 3km | 10km |
| 후보 반경 | 6km. 후보가 탭당 30곳 미만이면 9 → 12km로 확대, 그래도 모자라면 있는 만큼 | 제한 없음 |
| 거리 점수 | 1km 0.72 · 3km 0.37 · 6km 0.14 | 1km 0.90 · 5km 0.61 · 10km 0.37 · 20km 0.14 |
| 동선에서 | 숙소를 중심으로 짧게 돌아오는 구성 | 인기 장소를 먼저 고르고, 날짜별 군집으로 이동을 줄임 |

- 가중치 합은 항상 1이다 (코드가 로드할 때 검사한다).
- `any`에서도 거리를 0으로 두지 않는다. 숙소에서 너무 먼 곳이 인기 순위에서 뒤섞이는 것을 막고, 점수 동률을 가르는 용도다.
- 기본 모드와 모든 수치는 시작값이다. 샘플 일정 평가(§10)로 조정한다. spec의 기존 값(0.30/0.30/0.25/0.15, d0=5)은 두 모드 사이 중간값에 해당한다.

## 4. 점수 계산

```
score = w_theme × theme + w_pop × popularity + w_dist × distance + w_q × quality    (각 요소 0~1)
```

### 4.1 후보 필터 (하드 규칙, 점수 계산 전)

| 규칙 | 비고 |
|---|---|
| 서울이 아님 / 좌표 없음 / 비표출(`showflag=0`) 제외 | |
| 좌표 이상치 제외 | 서울 외곽 박스 밖. 실측에서 이상치 10건(9건은 동일 기본값 117.99/19.69) |
| 제외 분류: 숙박 `AC`, 사후면세점 `SH04` 계열 | **충돌**: spec §5A.2 표는 `SH04`를 쇼핑에 포함, Notion 실측은 제외(4,104건). 제외 쪽을 제안한다 (§12). 결정 전까지 `theme_map.json`은 spec대로 포함 |
| 테마 불일치 제외 | 카테고리 탭에서는 탭 분류에 속하면 통과 |
| 여행 기간 **전체**가 휴무면 제외 | 일부 요일만 휴무면 제외하지 않고 "화 휴무" 태그 |
| 행사(축제)는 기간이 여행 기간과 겹치지 않으면 제외 | 실측: 축제 189건 중 상당수가 종료됨 |
| 반경 밖 제외 (`near` 모드만) | §3 |

운영시간이 **알 수 없음**이면 제외하지 않는다. 자유 텍스트라 파싱이 안 되는 경우가 많고(단순형은 12~32%), 모르는 것을 닫힌 것으로 취급하면 후보가 너무 줄기 때문이다. 대신 quality를 낮추고 "운영시간 확인 필요" 배지를 단다.
폐업 여부를 알려주는 필드는 TourAPI에 없다. 사용자 신고와 갱신일(`modifiedtime`)로 보완할 수 있고, MVP에서는 한계로 둔다.

### 4.2 요소 정의

**theme** = (선택한 테마 중 이 장소와 매핑된 테마의 강도 합) ÷ 선택한 테마 수.
강도는 핵심 분류 1.0, 인접 분류 0.6 (예: 카페 테마에서 `FD05`는 1.0). 카테고리 탭에서는 탭 분류에 속하면 1.

**popularity** — 두 축을 합친다. 둘 다 0~1이고, 후보 내 최대값으로 나눠 정규화한다.

```
steady = 0.6 × region_pop + 0.4 × place_pop        (place_pop 없으면 region_pop)    ← spec §5A.2 ④ 그대로
base   = (1 − km) × steady + km × korean_signal     (km = korean_mix. 한국인 신호 출처가 정해질 때까지 0)
pop    = min(1, base + viral_bonus × viral)         (viral = 관리 목록 등재 여부, 보너스 0.15)
```
- `region_pop`: 서울관광 실태조사의 국적 권역별 방문지 통계(소표본 보정, spec ③). `place_pop`: 장소 단위 입장객 통계의 백분위(있는 곳만).
- `viral`(SNS 화제): 외부 SNS를 수집하지 않는다(약관·계정 제한). 팀이 관리하는 `place_trend` 목록(장소, 출처 URL, 확인일, 만료일 60일)에 있을 때만 켠다. 보너스를 점수에 넣을지 배지로만 쓸지는 팀 결정이다 (§12).
- 통계가 없는 장소는 `neutral_when_unknown`(0.30)을 쓴다. "방문객이 많이 찾는 곳" 태그는 통계가 있을 때만 표시한다.
- 혼잡도(실시간)는 순위에 넣지 않는다. 시각에 따라 바뀌는 값이라 순위가 흔들린다. 동선 화면의 시간대 힌트와 배지로만 쓴다(2차).

**distance** = `exp(−d ÷ d0)`, d는 숙소와의 직선거리(km). 순위 단계에서는 직선거리만 쓴다 (후보 수백 곳에 ODsay를 부르지 않는다).

**quality** = 사진 0.25 + 운영시간 0.25 + 입장료 0.25(입장료가 해당되지 않는 유형은 자동 충족) + 사용자 언어 설명 0.25.
운영시간은 구조화되면 0.25, 자유 텍스트만 있으면 0.15, 없으면 0.

### 4.3 다양성 보정

"전체" 탭에서만. 점수 순으로 한 곳씩 뽑을 때마다, 남은 후보 중 **같은 세부 분류**의 점수에 0.8을 곱한다. 순위는 보정 후 점수(final) 기준이다. 카테고리 탭은 보정하지 않는다.

### 4.4 추천 이유 태그

요소별 기여(가중치 × 값)가 큰 순으로 상위 2개 (theme, popularity, distance만. quality는 태그로 쓰지 않음).
문구 예: "숙소에서 1.2km", "일본인 인기 지역", "쇼핑 테마" (Figma 02c 카드 태그와 같은 형식). 근거가 없는 태그는 만들지 않는다.

### 4.5 선택: 평점·리뷰 (Google, 스파이크 후 결정)

켜면 popularity의 steady를 `0.85 × steady + 0.15 × review`로 바꾼다.
```
bayes  = (R × v + C × m) ÷ (v + m)      R 평점, v 리뷰 수, C 전체 평균 평점, m = 50
review = clip((bayes − 3.0) ÷ 2.0, 0, 1)
```
리뷰가 적은 곳이 5.0점으로 상위에 오르는 것을 막는 보정이다. 이름·좌표 매칭 정확도, 비용, 약관 확인이 선행조건이다.

## 5. 예시 (참조 구현 실행 결과, 가상 데이터)

가상 장소 14곳, 숙소는 명동 부근, 테마 = 문화역사 + 카페. 거리는 숙소 기준 직선거리.

| 순위 | 숙소 근처 (최종 점수) | 거리 | 상관없음 (최종 점수) | 거리 |
|---|---|---|---|---|
| 1 | 명동 카페 A 0.813 | 0.1km | 종로 궁궐 0.808 | 1.8km |
| 2 | 명동 성당 부근 유적 0.757 | 0.5km | 성수 카페 0.775 (화제 가산) | 6.8km |
| 3 | 종로 궁궐 0.715 | 1.8km | 명동 성당 부근 유적 0.715 | 0.5km |
| 4 | 을지로 카페 0.697 | 0.8km | 서대문 형무소 역사관 0.676 | 2.6km |
| 5 | 서대문 형무소 역사관 0.594 | 2.6km | 을지로 카페 0.676 | 0.8km |

- 같은 장소의 점수가 모드마다 달라지는 것을 확인했다. 궁궐은 `near`에서 거리 때문에 3위, `any`에서 인기 1위다.
- 명동 카페 B는 가중합 0.742인데 6위(0.593)다. 같은 분류 카페가 이미 상위에 있어 다양성 보정(×0.8)이 걸렸다.
- 숫자는 가상 데이터라 의미가 없다. 구조와 모드 차이를 보는 용도다.

## 6. 동선: 날짜 배정, 하루 순서, 제약

### 6.1 날짜별 묶기 (spec §5A.5 확장)
1. 선택한 장소를 좌표 기준 k-means로 `k = 여행 일수`개 군집으로 묶는다 (초기값은 가장 먼 점 순으로 고정).
2. 한 군집이 하루 상한(속도별 장소 수)을 넘으면 중심에서 가장 먼 장소를 가장 가까운 다른 군집으로 옮긴다.
3. 군집을 날짜에 배정할 때 **비용이 가장 작은 배정**을 전수 비교한다 (일수 7 이하).
   비용 = 휴무 요일 충돌 장소당 1000 + 비 예보일의 실외 장소당 20.
   예시 실행에서 궁궐은 화요일 휴무라 수요일(비 예보)에 배치됐다. 휴무 충돌을 비 예보 벌점보다 우선한 결과다.

### 6.2 하루 순서 (spec §5A.6 개선)
- 7곳 이하는 **모든 순열을 평가**한다 (7! = 5,040가지). 최근접 이웃 + 2-opt보다 정확하고 구현이 단순하다. 8곳 이상은 최근접 이웃으로 대체한다.
- 비용 = 총 이동 분(숙소 출발·복귀 포함) + 대기 분 + 위반 × 30 + 고강도 연속 × 30.
- 위반: 운영 시작 전 60분 넘게 대기, 운영 종료 후 도착·체류, 휴무 요일.
- 이동 시간 추정(순서 결정용): 직선거리 ≤ 1km면 도보(우회 1.3배 ÷ 4km/h), 초과면 대중교통(우회 1.3배 ÷ 18km/h + 8분, 도보 0.5km). 확정 후에는 구간별로 ODsay를 호출해 실제 값으로 교체한다. 700m 이내 구간은 ODsay가 -98을 돌려주므로 추정식을 그대로 쓴다.
- 식사 삽입(11:30~13:30, 17:30~19:30)은 spec §5A.6 단계 4를 따르며 참조 구현에는 아직 없다.

### 6.3 체력 조절

| 속도 | 하루 장소 수 | 도보 상한 | 고강도 장소 상한 |
|---|---|---|---|
| relaxed | 3 | 4km | 1 |
| normal | 4 | 6km | 2 |
| packed | 6 | 9km | 3 |

- 장소별 **활동 강도**(1 낮음 / 2 보통 / 3 높음)를 분류 코드로 부여한다 (궁궐·산책로·테마파크 3, 박물관·시장 2, 카페·전망대 1 등). `config/`에 `intensity.json`을 추가해 `stay_minutes.json`과 같은 방식으로 관리한다.
- 고강도 장소가 연달아 오면 순서 비용에 벌점을 줘서 사이에 낮은 강도 장소를 끼운다.
- 상한을 넘으면 자동으로 장소를 빼지 않는다. 경고 배지("도보 7.2km, 상한 6km")를 달고 사용자가 고른다. 사용자가 고른 것을 시스템이 지우면 신뢰가 깨진다.

### 6.4 날씨
- 비 예보(강수확률 60% 이상)인 날은 실외 장소에 벌점을 줘서 맑은 날로 옮긴다. 실내/실외 태그는 분류 코드로 1차 구분하고 애매한 곳은 수동 보정한다.
- 날씨 소스는 **기상청 단기예보**(공공데이터포털)를 후보로 본다. 이 문서에서는 응답 구조를 확인하지 못했다 ❓ (`api_schema.md`에 추가 예정). 예보 범위를 벗어난 날짜는 "예보 없음"으로 두고 벌점을 적용하지 않는다.
- 순위 화면은 날짜와 무관하므로 날씨를 점수에 넣지 않는다. 날짜 배정 단계에서만 쓴다.

### 6.5 사후 검증
동선 확정 후 모든 장소에 대해 요일 휴무, 운영시간, 행사 기간을 다시 검사한다. 해결되지 않으면 경고 배지를 단다 (F3-5). 이 검사는 LLM이 아니라 규칙 코드가 한다.

## 7. MVP 범위

| 포함 (LLM 없음) | 제외 또는 후속 |
|---|---|
| 필터, 점수 4요소, 두 모드, 다양성 보정, 이유 태그(템플릿) | 평점·리뷰 점수 (스파이크 후) |
| 날짜 묶기, 순열 탐색, 운영시간·휴무·체력·비 예보 반영 | 실시간 혼잡도 점수화 (배지만 2차) |
| 추정식 이동시간 → 확정 구간 ODsay | 식사 자동 삽입 (spec에 있음, 구현 후속) |
| 네이버지도 길찾기 리디렉션 | 사용자 행동 기반 가중치 학습 (v2) |

## 8. 선택적 LLM 계층

기능 플래그(`LLM_ENABLED`)로 켜고 끈다. 끄면 사용자에게 보이는 차이는 문장 품질뿐이다. 추천 결과와 동선은 같다.

| # | 용도 | 입력 → 출력 | 안전장치 |
|---|---|---|---|
| ① | 자연어 취향 → 조건 | "조용한 카페랑 궁궐, 천천히" → `{themes, mode, pace, must_include, avoid}` JSON | 스키마의 열거값만 허용. `must_include`는 DB 장소명과 매칭되지 않으면 버리고 사용자에게 알림. 실패하면 일반 입력 폼으로 돌아감 |
| ② | 추천 이유 문장 다듬기 | 이유 태그 + 사실값(거리, 휴무 요일 등) → 40자 이내 문장 | 출력 속 숫자와 장소명이 입력 사실에 없으면 폐기하고 템플릿 사용 |
| ③ | 장소 설명 요약·번역 보조 | 개요 텍스트 → 두세 줄 | 원문과 함께 보관, 번역은 Papago와 비교해 한쪽 선택 |

공통 규칙
- LLM은 좌표, 시각, 가격, 순위를 생성하지 않는다. 숫자는 코드가 넣고 LLM은 문장만 쓴다.
- 숙소 주소 등 개인 위치정보는 보내지 않는다 (거리 값만).
- 응답 대기 3초 제한, 실패하면 템플릿으로 즉시 대체한다.
- (장소, 언어, 태그 조합)별로 결과를 캐시한다. 10곳씩 묶어 한 번에 호출한다.
- 켜기 전에 템플릿 문장과 LLM 문장을 팀이 맹검 비교하고, 비용 상한을 정한다.

취향 JSON 스키마(①)
```json
{
  "themes": ["shopping", "experience", "food", "festival", "history", "nature", "leisure", "culture"],
  "mode": "near | any",
  "pace": "relaxed | normal | packed",
  "must_include": ["장소명(문자열)"],
  "avoid": ["theme 열거값"]
}
```

## 9. 데이터 요구사항

| 필요한 값 | 출처 | 상태 |
|---|---|---|
| 좌표, 분류, 사진, 설명, 시군구, 표출 여부 | `KorService2` 목록·공통 | ✅ 적재 가능 |
| 운영시간·휴무일 | `detailIntro2` 자유 텍스트 | ⚠️ 구조화 파싱 필요 (단순형 12~32%) |
| 입장료 | 관광지는 `detailInfo2`, 문화시설·레포츠는 `detailIntro2` | ⚠️ 구조 다름 |
| 국적별 지역 인기도 | 서울관광 실태조사 원자료 | ❓ 컬럼 코드표 필요 |
| 장소 단위 입장객 | 서울시 주요관광지점 입장객 | ❓ |
| 지역↔장소 매핑 `place_area` | 팀이 작성 (20~30개 지역부터) | 작업 필요 |
| 활동 강도, 실내/실외 | 분류 코드 규칙표 (`intensity.json`) | 작업 필요 |
| 화제 목록 `place_trend` | 팀이 관리 | 담당자 필요 |
| 날씨 | 기상청 단기예보 | ❓ 미확인 |
| 영문 장소명·설명 | 영문 TourAPI | 팀 확인 중 (`api_schema.md` §4) |

`place` 테이블에 추가할 컬럼 제안: `hours_state`(structured/text/none), `open_min`, `close_min`, `rest_days`(요일 배열), `intensity`, `indoor`, `area_id`, `pop_region`, `pop_place`, `trend_until`. 코드 값은 `ranking.json`과 `intensity.json`을 따른다.

## 10. 검증 계획

- 단위 검사: 가중치 합 1, 거리 감쇠 값(1km, d0=5 → 0.82), 모드별 점수 범위 0~1. 참조 구현의 자체 검사에 있다.
- 샘플 일정 평가(spec §5A.11): 국적 2 × 테마 조합 5 × 일수 2 = 20개를 두 모드로 만들어 팀이 "다닐 만한가 / 테마에 맞는가 / 이동이 과한가"를 1~5점으로 평가한다. 3.5점 미만 항목의 가중치·상한을 조정하고 변경 이력을 남긴다.
- 실데이터 점검: 서울 적재 후 모드별 상위 20곳을 직접 보고 이상한 장소(폐업, 제외 대상, 좌표 오류)를 찾는다.
- 회귀: 같은 입력이면 같은 순위가 나와야 한다 (군집 초기값 고정, 정렬 동률 규칙 고정).

## 12. 팀이 정할 것

1. 기본 모드를 무엇으로 할지 (제안: 숙소 근처). 숙소를 못 정한 사용자는 권역만 입력하는 경로. **Figma에는 모드 토글이 없어 `any` 화면을 추가할지, 모드를 삭제하고 `near`만 둘지 정해야 한다.**
2. 모드별 가중치·d0 수치 (표 3절은 시작값).
3. 사후면세점 `SH04` 제외 (spec 표와 Notion 실측이 충돌). 명동·인사동 매핑(`EX07`), 축제·레포츠(`EV`, `LS`) 포함 여부.
4. SNS 화제를 점수에 넣을지 배지로만 쓸지, `place_trend` 담당자.
5. 한국인 방문 신호의 출처 (정해지면 `korean_mix`를 0.3으로).
6. 속도 3단계의 상한값과 기본값.
7. Google 평점 스파이크 결과 (10/17 목표), 날씨 API 선정.
8. LLM을 MVP 시연에 켤지 (켠다면 ①만 우선 제안: 입력 해석이 가장 큰 가치).
9. Figma 테마 8종 매핑 확정. 이전 "감성 카페"는 음식(`FD05`)으로 합쳤고 "인생샷"은 별도 테마가 없어졌다. 축제/공연/행사(`EV`)는 기간 필터가 필요하고, 레저 스포츠(`LS`)·체험 관광(`EX`)은 이전에 제외 목록이었던 것을 포함하도록 바꿨다. `config/theme_map.json` 참고.
10. 장소 카드 태그(예: "일본인 인기 지역", "외국인 입장객 상위")는 근거 통계가 있을 때만 만든다 (spec F2-9).
